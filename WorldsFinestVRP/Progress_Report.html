What v4 does

Classical Solomon I1 (Solomon 1987, OR 35(2)) sequential insertion with:

  • Seed: farthest-from-depot unrouted customer, tie-break earliest due time
  • Insertion scoring: c1 = α₁·c11 + α₂·c12 (c11=distance increase, c12=push-forward in arrival at successor); c2 = λ·d(0,u) − c1 (urgency)
  • Default params (Solomon's "I1" config): μ=1, α₁=1, α₂=0, λ=1
  • Scale optimization: per-route, score only nearest_k=24 unrouted to current route endpoints (avoids O(N²·K) blowup at N=1000)
  • Polish: optional one pass of two_opt_intra per route

Constraint composition: v4 only checks TW + capacity (the hard feasibility constraints) at construction time. The 17-term cost catalog (embargo, skills, mixed_fleets, etc.) acts via the bandit refinement that follows, exactly as it does after pyvrp construction. v4 is now plumbed into portfolio_pyvrp_warm.solve_auto() as construction="fast_construct_v4".

Under heavy cost-term constraints (iter-7-v4-cost-aware): 81% gap recovery

The same embargo-aware 6-instance bench was repeated after landing the cost_aware flag on fast_construct_v4.solve() (default ON). The flag extends the I1 insertion score so c1 includes the per-visit embargo penalty for the inserted customer's arrival time: I1 actively avoids embargo windows at construction. v4 wins now jumped from 0/6 to 2/6, mean delta closed from −$648 to −$120/inst (81% recovery):

AGGREGATE 0/6, −$648 mean 2/6, −$120 mean +$528/inst, 81% gap closed

How it works: in the I1 insertion loop, each candidate (u, pos) is scored c1 = α1·c11 + α2·c12 + cost_weight · embargo_delta(u, pos). The embargo_delta is a cheap single-customer check: does u's new arrival time fall in any embargo window? If yes, add the per-visit penalty to the score. I1 then naturally picks positions that don't trigger the penalty. Wall overhead is ~6% (the window check is O(num_windows) per candidate, dominated by the existing arrival-time computation).

What's still on the table: at N=1000 v4 still trails pyvrp by $130-$507/inst -- the single-customer check misses push-forward into other customers' embargo overlap, and pyvrp's deeper HGS construction may still have a topology advantage. Future iterations: (1) full push-forward-aware embargo check (re-walk the route's new arrival times), (2) extend cost_aware to skills + mixed_fleets, (3) explore multi-start v4 with cost_weight sweep.

iter-7-v4-pushfwd (2026-05-16): push-forward-aware embargo was a wash

Interpretation: push-forward awareness trades N=500 wins for N=1000 wins. At N=500, it makes I1 over-cautious (avoiding insertions with small push-forward into embargo windows that the bandit could easily refine away later). At N=1000 where routes are longer, push-forward accurately captures the real cost. This isn't a clean improvement -- it's a different distribution of the same total error.

Decision: keep push-forward as default (more principled semantically, better at the harder N=1000 problem-sizes that matter most for production); accept that v4 sits ~$130/inst behind pyvrp under embargo, regardless of which variant. The remaining gap appears to be a fundamental construction-style difference (I1 single-sweep vs HGS multi-pass LS) rather than something a better insertion score can close. Next investigation should pivot to multi-start v4 or extending cost_aware to skills/mixed_fleets, not further embargo-score tuning.

Production guidance (updated):

  • Use pyvrp warmstart (default) when PyVRP is available and the last $120/inst matters; or for baseline workloads where v4 ties pyvrp already.

Iteration 6a-2-refresh (2026-05-16) — Architectural-drift fix

Conditional operator registration: drift fix + 12-test guard

Mid-session multi-seed re-run of iter-6a-2 embargo (originally 6/6 +$1,797/inst) produced only +$798/inst — a 56% magnitude drop. Same code path, same instance, same seed — different magnitude. Root cause: pm.solve was unconditionally registering the three meta-recipe operators (shift_start, class_shift, depot_shift) in the bandit's arm pool even when their target constraint axes weren't active. Each operator no-ops correctly when its axis is off — but still consumes bandit-iteration budget when picked. Less per-arm exploration time for the operators that actually have work → degraded magnitude.

Fix: conditional registration based on Settings.economics inspection at solve time

Lives in svrptw/solvers/classical/portfolio.py::_filter_ops_pool. Pruning rules:

  • shift_start requires peak_hour_wage_multiplier != 1.0 + peak windows, OR embargo penalty + embargo windows.
  • class_shift requires non-zero mixed_fleets premiums, OR a skill_mismatch_penalty.
  • depot_shift requires inst.depots set with len ≥ 2.

Meta-recipe Step 0 remediation pattern (proven 3 times)

When a constraint's axis is auto-decided by the evaluator (not controllable via customer-reorder operators), Step 0 fails. Canonical fix:

  1. Add an explicit per-route field in Route (default = "auto" sentinel)
  2. Evaluator honors the field when set; falls back to auto otherwise
  3. Add a dedicated operator that sweeps candidate values
  4. Register the operator in pm._OPS
  5. (iter-6a-2-refresh addition): gate registration on axis being active so the bandit doesn't burn iterations on dead arms

K-fairness metric foundation (iter-5t/u, 2026-05-15)

Cost-quality split that drove iter-5p/q/s was a metric artifact

quality_index has Spearman ρ  +0.782 with K (route count) — ~60% of cross-solver variance is explained by how many routes you use, not solution quality. The Phase G fast_construct_v2 "wins quality" framing from iter-5o was an artifact: fcv2 used 1.7-3.3× more vehicles than solve_auto on every instance.

K-fair complement metric (quality_per_route) reverses the ranking: PyVRP and solve_auto tie at the top (0.0315 vs 0.0300), fcv2 drops to LAST (0.0149, worst per-route quality of any feasible solver). solve_auto wins cost AND ties for best per-route quality — no tradeoff to optimize away.

Per_route_fixed_cost validation (iter-5u): under PyVRP's blind objective both solvers tie at $0/route; once routes are priced at $25/$100, solve_auto's lead widens monotonically with the coefficient.
