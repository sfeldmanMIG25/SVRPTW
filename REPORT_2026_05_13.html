1. Executive summary

The repo's headline scientific claim at session end:

Across 160 v1 OSM instances spanning four sizes (N ∈ {50, 100, 200, 500}) and 8 cities, our portfolio (13-arm LinUCB bandit over construction + improvement + destroy operators) is on the (operational_cost, wall_clock_seconds) Pareto frontier on every instance versus the two external SOTA baselines we benched (PyVRP@30/60 — DIMACS 2024 VRPTW winner — and POMO v3). PyVRP strictly dominates portfolio on 0 of 160 instances; POMO strictly dominates portfolio on 0 of 160. Portfolio strictly dominates PyVRP on 111 of 160 (69 %).
Under a third axis — a blind multimodal LLM dispatcher-acceptance judge (Gemini Flash Lite seeing a route-quality-color rendered image plus a structured-markdown text channel; solver identity hidden; A/B side randomized) — across 96 authoritative pairs: portfolio wins 42 / 42 head-to-head pairs (100 %), auction_gart wins 38 / 38 (100 %), PyVRP wins 16 / 19 (84 %), greedy and POMO never win. Under this 3-axis (cost, wall, logic) Pareto frame, portfolio strictly dominates PyVRP on essentially every v1 instance.

1.1 What this means

The cost-axis claim is defensible against the published SOTA (PyVRP / HGS). The dispatcher-acceptance claim is defensible after two methodological corrections both originating from the user:

  • The original rainbow per-route palette was leaking "many routes" into the VLM's score and inflating PyVRP's logic preference. Replaced with info-bearing color (viridis on per-route load utilisation) + directional arrows + colorbar legend.
  • The original text channel exposed solver names. Anonymised to Plan A / Plan B with randomised A/B side.

Together these inversions flipped the logic-axis result from "PyVRP wins 8/8 by +0.61 mean gap" (rainbow + non-blind) to "portfolio wins 42/42, auction wins 38/38, PyVRP wins 16/19" (info-bearing + blind). The earlier finding was a rendering + identity confound, not a real signal.

4. Critical bugs found and fixed this session

4.1 Capacity feasibility — silent acceptance of overloaded routes

svrptw.solvers.common.solution.evaluate() was computing operational_cost from travel time + distance + missed deliveries + TW lateness, but never checking that route load ≤ vehicle capacity. Concrete observation on Manhattan N=50 I000 (cap=29):

solverroutesmean utilmax util
greedy110.961.00
portfolio@5110.961.00
lkh3@1 (pre-fix)7 1.501.66

LKH-3 was producing routes carrying 1.5× capacity and the evaluator silently accepted them — its "wins" on N=50 cost were artifacts of this bug. Fix: added per-route overload computation; operational_cost += hard_late_penalty × total_overload; feasible = (missed == 0 and total_late == 0 and total_overload == 0). Spec: SPEC-0-EVAL-01-capacity-feasibility.md.

Follow-up: LKH-3 wrapper was further fixed (RUNS=1 → 5, MTSP_MIN_SIZE=1). Post-fix LKH-3 is capacity-feasible but drops 93 % of customers at N=200 — the CVRPTW TW handling is not viable on tight-window OSM data. LKH-3 dropped from the headline comparison.

4.2 PyVRP wrapper — prize-collecting drop-customers default

The PyVRP wrapper had required=False with each customer priced at hard_late_penalty. Under tight time pressure PyVRP would drop ~7 customers per N=50 instance, each costing $1000 in our evaluator — inflating "PyVRP cost" by an order of magnitude. First v1 N=50 bench reported PyVRP mean cost = 8 017; with required=True it dropped to 808.7.

4.3 Rainbow rendering as a VLM confound

The legacy renderer assigned a distinct matplotlib.cm.tab20 color per route. With ~11 vs ~12 routes between portfolio and PyVRP, the VLM was reading "more rainbow density = messier" into solutions that were structurally equivalent. User's diagnosis: "LLM and users would hate needless confusing colors on screen so that isn't a fair test." Confirmed empirically: an A/B comparison showed PyVRP-wins-logic 8/8 with the rainbow render vs 0/15 with single-muted-color render — the preference flipped entirely from a rendering change.

Replaced with info-bearing rendering: viridis colormap on per-route load utilisation, directional arrows on each leg (matters for asymmetric VRPTW + one-way streets), colorbar legend, no numeric metrics in the title (those go in the text channel).

4.4 Non-blind text channel — solver-name leakage

The original solution_text.to_text() emitted a ## Solver section with the actual solver name ("portfolio@10", "pyvrp@30"). Gemini may have an a-priori brand preference (PyVRP = DIMACS winner). User flagged: "the tests should be blind, the LLM should not know what data comes from which model."

Fixed: to_text(blind_label="Plan A") writes anonymous labels. _judge_pair_combined now randomly swaps A/B sides per call to control for any residual ordering bias. Rationale captured into PreferencePair.rationale for visibility.

5. The multimodal split-channel logic-axis pipeline (most important methodological win)

Architecture, end-to-end:

bench JSON rows (cost-based solver outputs)
  │
  ▼
within-instance pair sampling, priority-sorted by cost-gap-magnitude
  │
  ▼
re-solve sol_a, sol_b deterministically  ◄── PreferencePair generation
  │
  ▼
render each with fair_mode=True
   - viridis(load_util) per route                 [IMAGE channel]
   - directional arrows on legs
   - colorbar legend
   - NO solver name, NO route count in title
  │
  ▼
solution_text.to_text(blind_label="Plan A/B")     [TEXT channel]
   - aggregate cost decomposition
   - per-route table (load, util%, dist, time, slack)
   - TW p50/p90
   - NO solver name in any field
  │
  ▼
randomize A/B side  (control for ordering bias)
  │
  ▼
single combined chat/completions call:
   [prompt + img_A + img_B] → PAIR_SCHEMA →
     { score_a, score_b, rationale, confidence }
  │
  ▼
unscramble swap if needed, persist PreferencePair with rationale

The split-channel design lets the VLM use vision for spatial reasoning (clustering, zig-zags, star topology) and text for precise numerics (cost, util, time-window slack). Captured rationales show the LLM is using both channels:

"Plan A is significantly more efficient than Plan B, reducing total distance by approximately 100 miles and operational costs by nearly 20 % while maintaining feasibility. Plan B shows poor vehicle utilization in routes 10 and 11 (specific util% cited), and exhibits a star-like routing pattern with excessive zig-zagging."

The LLM is computing percentage deltas (text), identifying low-utilisation routes by ID from the markdown table (text), and naming visual antipatterns ("star-like", "zig-zagging", "spatial clustering") (image). Real dispatcher-grade reasoning, not just parroting cost.

8. Open research questions for next session

  1. Should we add a fixed per-route cost to the cost model? Real dispatchers pay driver shift cost per vehicle activated, not just per-mile + per-minute. A small fixed cost per non-empty route would push portfolio toward fewer larger routes (matching auction_gart's pattern, which the LLM judge prefers slightly). SPEC-7-COST-01 implements an exponential underutilisation penalty but it's defaulted off; a route-fixed-cost is a different, simpler lever worth trying first.
  2. Train a v0 LogicStudent on the 96 blind labels we just collected. Validate Bradley-Terry convergence + held-out teacher agreement. If > 80 %, deploy in the plateau_basin_jump path in portfolio.py. (Training kicked off in background as the report was being written.)
  3. Scale labelling to 500 / 2 500 pairs (paid OpenRouter ~$10–60 for 5-voter committee). Free-tier OpenRouter rate-limits beyond Gemini-solo are too aggressive.
  4. POMO+EAS — inference-time gradient search over the policy logits (Hottung 2022). The cleanest fix for POMO's cost gap, but ~5–10× wall increase per instance.
  5. Replace LKH-3 with HGS-DIMACS as the third external baseline. LKH-3 is structurally not viable on tight-TW OSM (drops 93 % of customers at N=200).
  6. SPEC-7-ARCH-01 hyperparameter controller — POMO decoder head that predicts portfolio's destruction strength / regret-k / plateau-window online during search. To our knowledge novel; bounded ~150 lines + REINFORCE update.
  7. Three-axis Pareto bench at N≥100 once the LogicStudent ensemble is trained. Right now we have logic-axis data only for v1 N=50.

11. What I would do next if I had to bet

Two bets, in priority order:

  1. Add a per-vehicle fixed cost to the cost model (e.g. $50 per non-empty route, ≈ wage of a 4-hour shift). Hypothesis: the bench gap to PyVRP at N=200 (currently 45 % strict dominance, was 70 % at N=500) is partly because portfolio uses 1 more route than PyVRP at N=200 and the current cost model doesn't penalise that. A fixed-cost-per-route term would tighten portfolio at the medium-N regime where ties dominate.
  2. Implement POMO+EAS. Currently POMO is strictly dominated by greedy at N≥200. With EAS it should at minimum tie greedy (POMO's policy + EAS gradient steps should never produce a tour worse than POMO's own greedy). That would put POMO back onto the (cost, wall) Pareto frontier as the "fast + decent" option.

Both are bounded scope (1-2 days each), both have concrete acceptance gates (dominance % improvement vs current numbers), and neither depends on labelling capacity decisions.
